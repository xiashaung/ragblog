# RAG 知识库 · 完整技术方案（新手友好版）

> 本文完全基于当前代码实现整理，用「图书馆管理员」的比喻把每一步讲清楚。
> 核心文件：`app/services/rag.py`（整个系统的心脏）。

---

## 一、一句话理解这套系统在干嘛

把它想象成一个**超级图书管理员**：

- **建库（录入）** = 你把书（文档 / 图片 / 网页 / 问答对）交给管理员，他拆开、做卡片、贴上「内容指纹」放进书架。
- **检索** = 你提问，管理员先从上万张卡片里**粗筛**出一批可能相关的，再用**放大镜精挑**出最相关的几张。
- **回答** = 管理员把这几张卡片摊在桌上，让 AI 照着卡片**用自己的话**组织成一段有条理的答案，并告诉你「这段话来自哪本书」。

这就是 RAG（检索增强生成）的全部：**先查资料，再让 AI 看着资料回答**，避免 AI 瞎编。

## 三、数据是怎么存的（最基础，先看懂这个）

两张表（`app/models.py`）：

### 1. `knowledge_docs`（文档表）= 一本书一条记录

| 字段 | 含义 |
|------|------|
| `id` | 书的编号。规则：`kb-{标题的哈希}`，**同名即同 id**，所以重复上传 = 覆盖而不是翻倍 |
| `title` | 书名 |
| `provider` | 这本书是用哪个 AI 模型做的指纹（重要，见下文坑） |
| `content` | **原文全文**（分片会重叠没法还原，所以单独存一份，供编辑 / 重建用） |
| `metadata` | 附加信息：来源文件名、图片 URL、录入方式等 |

### 2. `knowledge_chunks`（分片表）= 一张卡片一条记录

| 字段 | 含义 |
|------|------|
| `text` | 卡片上的文字（一小段，约 500 字） |
| `vector` | 这段文字的「内容指纹」= 一串 1024 个数字（向量） |

> **什么是向量？（新手重点）**
> 把一段文字喂给 embedding 模型，它吐出一串固定长度的数字（这里 1024 个）。
> **意思相近的文字，数字也相近**。于是「找相关内容」就变成了「找数字最接近的卡片」——
> 这是整个检索的数学基础。

## 四、建库（录入）流程 —— 内容怎么变成卡片

**四种录入方式，最后都汇到同一个函数 `upsert_document`（rag.py:258）**，殊途同归不会走偏：

```
上传文件 / 纯文本 / 问答对 / 抓网页
          ↓
   [如果是图片 / PDF里的图] → 视觉模型生成中文描述，图片落盘存 URL
          ↓
   chunk_text() 把长文切成 ~500 字小片（段落边界切，带重叠防止切断语义）
          ↓
   embedding 模型给每片算出 1024 维向量
          ↓
   存进 knowledge_chunks 表
```

### 图片的巧妙处理（`app/routers/upload.py`）

图片本身没法算文字向量，所以：

1. 让视觉模型用中文**描述**这张图（这段描述可被检索）；
2. 原图**落盘到 `media/uploads/` 存成文件 URL**，数据库只存 URL 不存图片二进制（避免数据库撑爆）；
3. 前端检索命中时，能顺着 URL 把图显示出来。

> ⚠️ **一个必须懂的坑**：换 embedding 模型 = 指纹体系变了，旧卡片全部作废，必须「重建索引」。
> 每张卡片记录了自己的 provider，检索时只查「跟当前配置同一个 provider」的文档。

## 五、检索流程 —— 这套方案的精华（三段式）

代码在 `search()`（`app/services/rag.py:709`）。为什么需要三段？打个比方：

- **向量检索**像「凭印象找书」——快，但可能记岔，找些「看着像」的。
- **关键词检索**像「按书名精确查」——能找到向量忽略的具体词、编号。
- **精排**像「把候选书一本本翻开比对，确认到底哪本最切题」。

单用向量「不够准」，所以三段叠加：

```
你的问题
  ├─① 向量召回：算问题指纹 → 找数字最接近的若干卡片 (pgvector，库内算 + HNSW 索引)
  ├─② 词法召回：Postgres pg_trgm 三元组相似度 → 找字面最像的若干卡片
  ↓
  ③ RRF 融合：把两份榜单按名次合并（两榜都靠前的大大加分）
  ↓
  ④ 精排 rerank：cross-encoder 模型把 (问题, 卡片) 成对深度打分，取最准的 top_k
```

| 段 | 函数 | 说明 |
|----|------|------|
| ① 向量召回 | `_search_pgvector` / `_search_in_python` | 数据库用 `<=>`（余弦距离）直接排序取前几名 |
| ② 词法召回 | `_search_lexical_pg` | 用 `word_similarity(query, text)` |
| ③ 融合 | `_rrf_fuse` | Reciprocal Rank Fusion，只看名次不看分数 |
| ④ 精排 | `_rerank_hits` → `reranker.py` | 调 OpenAI 风格 `POST /rerank` 端点 |

### 为什么词法用 pg_trgm 而不是标准 BM25 / tsvector？

你的内容全是中文，而原生全文索引要把词用空格分开，**中文没空格会被当成一个整词、根本搜不中**。
pg_trgm 把文字切成「三个字一组」的小片段来比对，**不需要分词也能命中中文关键词**，
是这套代码针对中文的务实选择。（真·BM25 要装 ParadeDB 扩展，目前没装。）

### RRF 融合为什么这样算？

公式：`每榜得分 = 权重 / (60 + 名次)`，两榜累加。
好处是**避开了「向量分」和「词法分量纲不同没法直接比」的问题**——只用名次。

### 每一段都能单独开关、失败自动回退

- 向量 / 词法召回某段挂了 → 用能用的那段；
- 精排服务挂了 → 退回融合顺序；
- 非 Postgres（如 SQLite 测试）或 pg_trgm 缺失 → 词法腿自动跳过，退回纯向量。

任何一环坏掉，检索照常出结果。

## 六、回答生成 —— 看着资料答题（`rag.py:793 answer()`）

```
检索命中的 top_k 段文字 → 拼成 Context（标上编号 [1][2]...）
        ↓
System 提示词（RAG_SYSTEM_PROMPT）要求 AI：
   1. 用自己的话理解整合，别照抄
   2. 内容长就用小标题 ### + 列表组织
   3. 引用某段结论时句末标 [n]
   4. 资料里没有的，明说「知识库中未找到」，不许编
        ↓
（可选）问题带图片 → 一起喂给视觉模型
        ↓
大模型生成结构化答案 + 附引用来源（可点开的文档标题）
```

这段提示词就是**「答案为什么有条理、不胡说」的关键**。


## 九、新手最容易踩的 3 个坑（务必记住）

1. **改了后端代码没重启** → 后端 `uvicorn` 不带 `--reload`，必须手动重启才生效。
2. **改了前端没重新构建 + 没硬刷新** → 前端由后端直接托管 `web/dist`，要 `pnpm build` 后浏览器 `Cmd+Shift+R`。
3. **换了大模型 / 嵌入模型后要「重建索引」** → 否则文档是旧指纹，检索不到（概览页会标 `stale`）。

## 十、术语速查表

| 术语 | 通俗解释 |
|------|----------|
| RAG | 先检索资料、再让 AI 照着资料回答 |
| Embedding（向量） | 把文字变成一串数字，意思相近则数字相近 |
| Chunk（分片） | 长文切成的 ~500 字小段，检索的最小单位 |
| pgvector | Postgres 里存向量、算相似度、建索引的扩展 |
| HNSW | 一种向量索引结构，让「找最接近的」更快 |
| 词法检索 / trigram | 按字面（三字一组）匹配关键词，补向量的短板 |
| RRF | 把两份榜单按名次融合成一个排序的算法 |
| Rerank（精排） | 把问题和候选成对喂给模型，深度打分定最相关的 |
| provider | 用哪家的模型（openai / deepseek / qwen / ollama / mlx / mock） |
| stale | 文档向量属于旧 provider，需重建才能被检索到 |
