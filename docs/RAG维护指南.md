# RAG 知识库 · 维护指南（新手版）

> 面向**没做过 RAG、只想接手维护**的人。
> 本文不讲解原理，只讲"平时要做什么、出问题了怎么办"。
> 原理部分见同目录 `RAG技术方案.md`。

核心代码：`app/services/rag.py`（入库 + 检索 + 回答）、`app/services/rag_queue.py`（后台队列）。

---

## 一、先记住一句话

这套东西干的事很简单：

> **先检索到相关资料 → 再让 AI 根据资料回答，不让它凭记忆瞎编。**

存的时候：每份文档切成小段，每段算一串"指纹数字"（向量）。
查的时候：把问题也变成同样的数字，找最近的几段。
答的时候：把这几段当参考资料交给 AI，并要求它标注出处。

你不需要搞懂向量怎么算——**出问题再去查那一块就行**。

---

## 二、先搞清"数据存在哪"（4 张表）

都在这 4 张表里（`app/models.py`）：

| 表 | 一句话 | 你什么时候会跟它打交道 |
|----|--------|------------------------|
| `knowledge_docs`（文档） | 一份文档：标题、原文、当前状态 | 列表、详情、改内容 |
| `knowledge_chunks`（分片） | 每份文档切成的小段，**每段有一个向量** | 搜索就搜这张表 |
| `knowledge_images`（图片） | 文档里的图，**图也有向量** | 文搜图；别和文本向量搞混 |
| `rag_tasks`（任务登记） | 每次上传/编辑/重建都登记一条 | 上传后卡在进度、查队列 |

> ⚠️ 一个坑要刻在脑子里：**向量是按"嵌入模型"算的，每张文档记了一个当前状态（status）。**
> 状态有四种，代码用它们盯"向量化做到哪一步了"：
> - `indexed` — 已学习，**能被搜索**
> - `pending` — 待重建（新建还没学习 / 刚换完模型）
> - `processing` — 正在重建
> - `failed` — 重建失败（常见：维度不符）
>
> 记住：**只有 `indexed` 的文档才会被搜到**，其它三种搜不到是正常的。

## 三、日常要做什么（运维清单）

### ✅ 1. 文档怎么来的（4 种录入方式）

入口都是管理后台知识库页（`/admin`）。支持：

- 上传文件
- 直接贴文本 / Markdown
- 批量问答对
- 输入网页链接自动抓取

> **同一个标题重复上传 = 整篇替换，不会重复堆一份**——这是设计如此，放心用。

### ✅ 2. 上传是"异步"的，别点了就以为好了

点了上传：

1. 接口立刻返回一个 **`task_id`**；
2. 任务丢进**后台队列**，由 Worker 去干三件事：切块 → 算向量 → 入库（这几步慢）；
3. 前端需要**轮询** `/knowledge/tasks/{task_id}` 看进度。

默认 **2 个 Worker 并发**（`APP_RAG_QUEUE_WORKERS`）。

> 现象：上传后列表里文档状态一直挂着 `pending` 不动 → 多半是 Worker 挂了 / 队列停了（见下方"排查"）。

### ✅ 3. 配置：改这里要重启

配置来自 `.env`，前缀 `APP_`，改完**必须重启服务**才生效。

和知识库**直接相关、且只能在 .env 改**（结构性参数，不能在线改）：

| 配置项 | 含义 |
|--------|------|
| `APP_RAG_VECTOR_DIM` | 文本向量维度，**换嵌入模型要一起改 + 重建索引** |
| `APP_RAG_IMAGE_VECTOR_DIM` | 图片向量维度 |
| `APP_RAG_QUEUE_WORKERS` | 队列并发度（默认 2） |

精排、混合检索等开关，走的是**运行时系统配置**（后台"系统配置"页 + `app/services/provider_store.py`），**以数据库配置为准，不是 .env**。别只盯着 .env 改。

## 四、出问题了怎么排查（重点）

### ❓ 1. 上传后文档一直 `pending`/`processing`，搜不到

**最可能的原因：后台队列 Worker 没在跑。**

排查步骤：

1. 看启动日志有没有这行：`RAG 队列 Worker 已启动（并发 N）`，没有就是队列没起；
2. 查 `rag_tasks` 表最新一条：
   - 一直 `running` 不动 → 某次任务卡死，Worker 可能崩了；
   - 大量 `pending` → 内存队列丢了（见下方"进程重启"）。
3. 确认服务在启动时起了队列（`main.py` lifespan 里起的）。

### ❓ 2. 全搜不到 / 一堆文档显示 `failed` —— 八成是换了嵌入模型

换 AI 的嵌入模型后，旧文档的向量维度对不上，会被统一置为 `pending`。

处理：

1. 调 `/knowledge/stats` 看统计，或用管理页看 `failed` 分布；
2. 触发**全库重建**：`POST /knowledge/reindex-all`（后台队列逐篇重建）；
3. 单篇重建：`POST /knowledge/{id}/reindex`；
4. 重建失败会写原因到文档 `meta["reindex_error"]`，看详情里这条字段就知道为啥失败（最常见是**维度不符**）。

> ⚠️ **维度不符的解决办法**（失败详情里会写明）：
> 改 `APP_RAG_VECTOR_DIM` → 跑一次 Alembic 迁移（`alembic upgrade head`）→ 全库重建索引。

### ❓ 3. 某文档"重建后变 failed，提示无原文"

文档太老、`content` 是空的（早期没有"存原文"这列），无法重建。

处理：**让用户重新上传**即可。代码里这种情况直接置 `failed` 并写明原因，不会卡死。

### ❓ 4. 搜出来的东西不相关 / 维度对不上

先看 `/knowledge/stats` 里回写的 `vector_dim` 和 `vector_backend`，确认维度一致。
另外"为什么两份文档搜不到"，常见是因为它们用了**不同的嵌入模型**或**维度不同**——这正是代码强调"不同模型向量不可比、不共存"的原因。

## 五、几个"别乱动"的约束（保命提醒）

1. **改表结构必须补 Alembic 迁移**，不能只改 `app/models.py`。新增/改向量列尤其谨慎。
2. **`.env`、`app.db`、`media/`、构建产物是运行数据，别手改、别提交。**
3. **向量列是定长的**：装不下别的维度会直接报 `ValueError` 而不是写脏数据——看到报错别慌，按上面的"维度不符"流程处理。
4. **图片向量和文本向量是两套、互不牵连**：图片后端没配 / 图片文件丢了，只记一条错误日志，不会让文本入库失败。看到图片相关的 `failed` 不必紧张，先保证文本能搜。
5. **删文档 = 先删分片/图片行，再删文档**（反序会留孤儿数据）；批量删逐个给结果、不整批回滚——这些锁死在 `app/services/rag.py`，别去绕过。
6. **改后端代码记得重启**（`uvicorn` 不带 `--reload`）；**改前端记得 `pnpm build` 后硬刷新**（`Cmd+Shift+R`）。

## 六、最小维护检查口诀

> 📋 上传卡住 → 查 Worker 队列在不在跑（看 `rag_tasks`）
> 📋 全搜不到 → 是不是换了嵌入模型（看 `failed`，触发 `reindex-all`）
> 📋 维度报错 → 改 `APP_RAG_VECTOR_DIM` + 迁移 + 重建索引
> 📋 改代码 → 先读相关服务/路由，别越层；改完跑 `./scripts/check.sh`
> 📋 加新能力 → 先在 `app/rbac.py` 登记权限，再到路由挂

## 八、进程重启的特别说明

内存队列丢了**不会丢任务登记**：

- 存盘的 `pending` 任务只会在启动时**告警**，不自动重跑——半截任务（比如已删旧分片、还没写新分片）重复跑比丢任务更糟；
- 这类情况交给管理员在后台确认后重新发起即可，不用慌。
